# Fork: measured speed and paired menu-bar rings

This contract overrides the upstream estimate rules in METRICS 6.3/6.5/9.5 and the token layout in DESIGN 3 for this fork. Product version stays at the upstream VERSION.

- For non-Codex transcript sources, a rate uses finalized usage and an observed decode interval: `[firstMs, endMs]`, or `[startMs, endMs]` when first-content timing is absent. Existing timing validation still applies. No historical, model or source fallback predicts an unfinished request's tokens, cost or thinking rate.
- Codex primary TPS and last-response TTFT use Agent Speed's independent OTLP/HTTP JSON receiver (`127.0.0.1:43181/v1/logs`), implemented on macOS and Windows. Pair `codex.websocket_request` / `/responses` API request events with `response.completed` usage events by conversation and model, using Codex's measured `ttft_ms`. Decode is `(output_tokens - 1) / (request_duration - TTFT)`. Full transcript item timestamps are not token-arrival timestamps and MUST NOT supply Codex primary decode speed or TTFT. Match completed telemetry to enabled local transcripts by thread, model, output count and completion time (within 100 ms); no cross-thread, remote-host or token-count substitution. Unmeasurable single-chunk bursts and missing transport timing do not enter the speed window. Before any valid sample, main rings show `—`.
- The receiver persists only measurements/identities in its own `codex-measurements.json` in the platform's Agent Speed data directory, bounded to 10,000 completions. No prompt or response text is stored. It never reads another TPS application's database. The optional loopback-only compatibility relay sends unchanged incoming OTLP batches to the previously configured local receiver; the relay's availability and data never affect Agent Speed's calculation. `scripts/configure-codex-telemetry.py` defaults to dry-run, validates and backs up the supported existing Codex configuration before changing only the exporter endpoint. Existing Codex processes may need restart; new processes load it directly. A listener conflict is reported by the diagnostic probe rather than silently stealing another application's port.
- The menu-bar/taskbar token rings and dashboard main token readout use a 30-second completion window (`MeasuredRateWindow`). Its end is the latest valid finalized response completion at or before the observation time, and its inclusive start is 30 seconds earlier. Select responses by completion time and use their full observed decode durations. For each Agent, divide its total confirmed output tokens by its total decode seconds; do not divide by 30 or average individual response rates. The analogous total-token field uses the same durations. This follows CodexTPS's latest-response window approach with the user-selected 30-second duration. Individual token arrival times are not available from completion-only transcripts.
- The left ring sums those per-Agent interval speeds; the right ring takes their arithmetic mean. Each Agent with valid positive output in the window counts once, including a parent and child independently. Waiting or unmeasured Agents do not enter the denominator. An empty initial state is zero. Advancing the clock alone does not move the window or decay its rates: hold the last measured result, including after transcript retention prunes old records. A new valid completion moves the window and refreshes both rings; invalid or unfinished responses cannot move it. Removing a host clears the retained result and recalculates from remaining records.
- Sources that only write usage at completion cannot supply a new measured speed before completion. Keep the last interval result (zero before any sample) rather than estimating and correcting later. Final usage arriving later replaces the record with the same key; re-reading does not add another response. Estimated snapshot/history fields remain for compatibility but are zero.
- The existing 3-second transcript-based `.live` telemetry and history chart remain for reporting compatibility; these legacy transcript timings are not the transport decode measurements used by the main rings and must not be treated as equivalent; they are distinct from the 30-second main token readout. Cost/thinking/network blocks retain their own windows. Estimated snapshot/history fields remain zero.
- macOS menu bar: two equal rings in the existing gauge style, left sum / right mean; each number is centered inside its ring. No separate token number, unit or TTFT. Token ring values and fills follow the observed snapshot directly, without a spring or historical prediction. Existing money/network/intelligence blocks remain separate.
- TTFT is the latest response's observed `firstMs - startMs`, shown in the dashboard popover and native hover tooltip, with `—` when unavailable. Do not substitute request duration or a forecast. Neither token ring has a TTFT label or latency value.
- Windows implements the same measured-only engine and mean. Its taskbar shows paired rings horizontally (stacked for a vertical taskbar); popup/hover retains TTFT. A real Windows desktop is still required for runtime visual acceptance.
